## 浏览器 DASH 和 M4A

当前扩展对 DASH 选取 H.264、HEVC 或 AV1 和独立 AAC。对应调用是 `combineTracks(video, audio)`，独立 AAC 则用 `remuxMedia(input, { tracks: REMUX_TRACK_SELECTION.audio, ... })`。`createOpfsStorage` 提供文件支持的样本与索引存储，输出仍为 fMP4/M4A。迁移可以移除直接依赖的 `mediabunny@1.62.1` 和扩展里的补丁维护。`media-remux` 内置基于 Mediabunny 1.66.2 的修改版源码，发布扩展时需保留对应的 MPL-2.0 声明。扩展选流见 `utils/bilibili/streams.ts`。 [合并实现](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/remux.ts#L193-L252) · [MP4 输入限制](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/input/mediaInput.ts#L177-L236) · [OPFS 存储](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/storage/opfs/createStorage.ts) · [第三方声明](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/THIRD_PARTY_NOTICES.md)

在现有 `remux.worker.ts` 中调用核心 API，可以沿用 `mergeBrowserMedia` 的 120 秒启动确认、任务取消、保存后的 OPFS 清理和 Chromium 的 `audio/x-m4a` 适配。进度取 `bytesProcessed`，它统计已复制的编码载荷。核心 API 会对时间轴做额外预检，包括视频起始关键帧、选中轨道的部分编辑列表和 AV1 解码时间轴，因此替换仍需覆盖浏览器里的真实素材和大文件。扩展目前通过 `useStreamReader: false` 读取 MP4，新库使用 vendored `BlobSource` 的默认策略，在部分浏览器会走 `Blob.stream()`。 [库 Worker 处理](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/browser/client.ts#L175-L302) · [轨道预检](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/mediaTracks.ts#L153-L245) · [MP4 读取](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/input/mediaInput.ts#L155-L166) · [读取器选择](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/vendor/mediabunny/src/source.ts#L368-L398)

## Progressive 和 FFmpeg

`concatMedia(inputs, { tracks: REMUX_TRACK_SELECTION.videoWithOptionalAudio, ... })` 可同时处理单段和多段，要求每段有视频，可保留音轨。MP4 按主轨规则选轨，当前 `progressiveMedia.ts` 中的 FFmpeg 固定取首视频和可选首音频。用首条音轨为 48 kHz、默认音轨为 44.1 kHz 的双 AAC 轨道 MP4 验证，WASM 保留 48 kHz，库保留 44.1 kHz。多段仍要求轨道布局、编码配置及显示属性一致，FLV 仍限于标准 AVC 和 AAC-LC。`durl` 选流目前只验证画质和 CDN 地址，因此会把更宽的素材范围送到封装层。库按各段所选轨道的呈现跨度计算接点，FFmpeg 采用 concat demuxer 的段时长，本仓库双段 MP4 和 FLV 样例的总时长实测有差异。 [可选音轨及拼接预检](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/remux.ts#L80-L128) · [选轨实现](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/input/mediaInput.ts#L177-L187) · [FLV 编码检查](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/input/flvInput.ts#L158-L191)

从 B 站旧版播放接口响应缓存的 `BV17x411w7KC` 360P progressive MP4（H.264 + AAC）触发了 `UNSUPPORTED_MEDIA_FEATURE`，具体原因是 MP4 编辑列表会裁剪样本呈现。当前扩展的 `runProgressiveFFmpeg` 可完成封装，产物可通过 FFmpeg 解码。另用合成的 H.264 + MP3 FLV 复现了 `UNSUPPORTED_CODEC`，现有 WASM 同样成功。若迁移 progressive，建议保留现有 WASM，只有明确的媒体兼容失败才切换后端，例如已复现的这两类错误。取消、配额和写入错误按原任务失败处理。切换前要释放本次输出句柄和临时存储，并评估 progressive 新增样本暂存文件的配额。 [编辑列表检查](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/vendor/mediabunny/src/isobmff/isobmff-demuxer.ts#L2661-L2684) · [公开错误码](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/constants.ts#L113-L146)

本地助手的 `scripts/native-downloader.py` 通过 Python 子进程调用系统 FFmpeg，三个任务类型都用 `-c copy -movflags +faststart` 输出普通 MP4/M4A。`media-remux` 的 JavaScript 核心始终输出 fMP4，接入 Python 还需要 JavaScript 运行时、定位文件读写适配和子进程生命周期集成。 [库输出参数](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/core/writeSegments.ts#L182-L208) · [磁盘适配器导出](https://github.com/ntnyq/media-remux/blob/f077b4402613ca34f96c8f627707327a81b0a467/src/index.ts#L13-L18)

## 本次验证

上游源码构建成功，234 项测试通过。使用构建产物与 Node 定位文件适配器验证了缓存的 B 站 AVC、HEVC、AV1 DASH、独立 AAC、单段 `durl` 和同一 `durl` 片段重放拼接。还覆盖了合成的分离 `.m4s`、长 GOP、双段 MP4/FLV、视频无音轨，以及缺少视频或轨道布局不一致的预检。成功样本的编码包 SHA-256 和顺序与输入一致，产物均通过 FFmpeg 解码。本次验证覆盖核心 API 和 WASM 封装，当前工作区的扩展接入及浏览器保存仍待迁移后验证。 [上游测试](https://github.com/ntnyq/media-remux/tree/f077b4402613ca34f96c8f627707327a81b0a467/tests)
